## 阶段9：多会话窗口与多任务并发

2026-11-03 用户要求纳入阶段计划。本次仅更新计划，尚未实现并发功能。
安排在阶段8审批—实施—验证闭环之后、整体验收之前；保留阶段5至8的核心能力推进顺序。
实现前先核对桌面全局运行状态、Runtime注册、任务租约、持久化与独立API Worker的现有能力，复用已有机制。

### 使用目标

- 用户可以同时打开多个会话窗口，分别选择项目、查看历史和执行任务；切换窗口不停止后台任务。
- 不同项目的不同会话可并行分析、诊断和开发；同项目不同会话也可以并行调查。
- 每个任务的对话、模型会话、知识、数据源绑定、搜索额度、进度、审批、停止和恢复独立，不使用全局“当前任务”串接请求。
- 同一任务同时只能有一个有效执行者；重复点击或在多个窗口打开同一任务，不能重复执行。

### 实施顺序与边界

| 步骤 | 变更内容 | 验收重点 |
| --- | --- | --- |
| 9.1 执行隔离与调度 | 按task ID管理运行实例、取消信号与事件；复用任务租约/版本检查。配置全局并发上限，超过额度排队；等待输入或审批的任务释放执行槽位，用户确认后重新调度 | 项目A等待审批时，项目B继续运行；同一任务不能被桌面/API重复领取；排队与运行状态区分 |
| 9.2 多会话窗口 | 会话窗口绑定固定项目和任务，按任务订阅进度；展示运行、排队、待审批、暂停等状态。停止/关闭单个任务窗口沿用该任务的停止保存语义；应用退出协调全部活动任务 | 无串话、无错误窗口审批、无全局停止误伤；关闭一个窗口不终止其他任务 |
| 9.3 共享代码目录协调 | 不同独立工作目录可并行开发；同一或重叠工作目录的修改、可能写文件的验证、Git/SVN更新及提交等互斥排队。锁定依据是实际路径及共享资源，而非仅项目名称/ID | 两个项目指向同一目录也不能并发覆盖；排队后重新核对文件指纹和审批依据，变化时重新分析/审批 |
| 9.4 调查一致性与资源限制 | 共享目录发生修改时，相关调查结果需重新核验；需要同项目同时修改代码时使用独立工作副本，再明确整合差异。Git可评估worktree，SVN评估独立检出，不强制项目改用Git。数据库连接/查询额度按实际数据源限制，模型调用按配置限流 | 不能读取到变化中的文件后仍宣称证据有效；不能共用游标/事务导致跨任务数据混用；不因多开窗口取消查询限制 |
| 9.5 并发恢复与验收 | 各任务独立保存事件和检查点，崩溃后核对租约、执行者及未知结果；复用现有审批和恢复流程，避免重复写入。记录排队时间、执行时间与资源占用 | 停止一个任务不影响另一个；断电后所有任务可追溯恢复；未知副作用先核对；单任务性能无明显退化 |

同项目并发不意味着允许多个会话同时改同一份代码。首版先支持并行调查和独立目录并行开发，
共享目录的写入按序执行；独立工作副本、冲突整合是同项目同时开发的后续步骤，不自动覆盖或合并用户修改。
数据库修复仍遵循阶段7、8的方案与审批边界，并发能力不授予新的数据库写权限。

### 验收场景

1. 两个不同项目的会话同时运行，知识、数据源、结果、进度和审批分别归属正确任务。
2. 同项目两个会话并行调查；一个进入修改时，另一个涉及相同文件的结论能识别变化并重新核验。
3. 两个会话对同一实际目录申请修改，按序执行；后执行任务不能使用已失效的方案审批。
4. 并发超过配置额度时有序排队，排队任务可取消，不占用模型调用额度或计入执行超时。
5. 停止、关闭单个窗口、重复打开同一任务、重复审批均不干扰其他任务或重复执行。
6. 多任务运行中重启/断电后逐项恢复，不自动重放结果未知的写入；比较并发与串行的正确性、延迟及资源占用。

下一步为阶段6；阶段9实施前再根据届时的调度、工作副本和部署形态细化实现，不提前增加运行时结构。
